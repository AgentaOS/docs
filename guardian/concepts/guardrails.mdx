# Guardrails, Not Gatekeepers

Before any transaction gets signed, Guardian checks it against your rules. Spending too much? Blocked. Sending to an unknown address? Blocked. Too many transactions per hour? Blocked. The server refuses to co-sign until every rule passes.

Every enabled rule is checked. If any rule fails, the server returns the full list of violations — not just the first one. You see exactly what went wrong.

<Warning>
  Guardrails only apply to signing paths that involve the server (Signer+Server and User+Server). The Signer+User offline path bypasses them entirely.
</Warning>

---

## How It Works

```mermaid
flowchart TD
    TX["Transaction arrives"] --> DECODE["Server decodes transaction\n(to, value, function, calldata)"]
    DECODE --> EVAL["Evaluate ALL enabled guardrails"]

    EVAL --> CHECK{All guardrails pass?}

    CHECK -- "Yes" --> SIGN["Server co-signs\n(threshold protocol)"]
    SIGN --> BROADCAST["Broadcast to Ethereum"]
    BROADCAST --> AUDIT_OK["Log: approved"]

    CHECK -- "No" --> REJECT["403 — all violations returned"]
    REJECT --> AUDIT_FAIL["Log: denied + violations"]

    style TX fill:#f5f5f3,stroke:#1a1a1a,stroke-width:2px
    style CHECK fill:#fff,stroke:#1a1a1a,stroke-width:2px
    style SIGN fill:#22c55e,stroke:#16a34a,color:#fff
    style REJECT fill:#ef4444,stroke:#dc2626,color:#fff
    style AUDIT_OK fill:#f5f5f3,stroke:#22c55e,stroke-width:1px
    style AUDIT_FAIL fill:#f5f5f3,stroke:#ef4444,stroke-width:1px
```

1. Transaction arrives at the server
2. Server decodes the transaction (to, value, function selector, calldata)
3. **Every enabled guardrail is evaluated against the transaction context**
4. If ALL guardrails pass — server proceeds to co-sign
5. If ANY guardrail blocks — 403 response with all violations, logged to audit

The response includes every violation, not just the first one. You see the full picture.

```json
{
  "statusCode": 403,
  "message": "Policy violation",
  "violations": [
    {
      "policyId": "pol_abc123",
      "type": "rule_reject",
      "reason": "Transaction value 5.0 ETH exceeds per-tx limit of 1.0 ETH",
      "config": { "type": "ethValue", "operator": "<=", "value": "1000000000000000000" }
    },
    {
      "policyId": "pol_def456",
      "type": "rule_reject",
      "reason": "Address not in allowlist",
      "config": { "type": "evmAddress", "operator": "in", "addresses": ["0x..."] }
    }
  ]
}
```

## Rules Engine

The rules engine is Guardian's policy system. You define an ordered list of rules. Each rule has criteria and an action (`accept` or `reject`). Rules are evaluated top-to-bottom. First match wins.

<Info>
  Rules are stored as a **policy document** per signer. One document, one ordered rule set. Supports draft/active versioning.
</Info>

### Criterion Types

| Type | What It Checks | Key Fields |
|------|---------------|------------|
| `ethValue` | Transaction value in wei | `operator`, `value` |
| `evmAddress` | Destination address | `operator` (in/not_in), `addresses` |
| `evmNetwork` | Chain ID | `operator` (in/not_in), `chainIds` |
| `evmFunction` | Function selector (4-byte) | `selectors` |
| `ipAddress` | Caller IP | `operator` (in/not_in), `ips` |
| `rateLimit` | Requests per hour | `maxPerHour` |
| `timeWindow` | UTC hour range | `startHour`, `endHour` |
| `dailyLimit` | Rolling 24h spend (wei) | `maxWei` |
| `monthlyLimit` | Rolling 30-day spend (wei) | `maxWei` |
| `maxPerTxUsd` | Per-transaction USD cap | `maxUsd` |
| `dailyLimitUsd` | Rolling 24h spend (USD) | `maxUsd` |
| `monthlyLimitUsd` | Rolling 30-day spend (USD) | `maxUsd` |
| `blockInfiniteApprovals` | Block unlimited ERC-20 approvals | `enabled` |
| `maxSlippage` | Max swap slippage percent | `maxPercent` |
| `mevProtection` | MEV protection enforcement | `enabled` |
| `evmAddressBlocked` | Blocked destination addresses | `operator` (in/not_in), `addresses` |
| `maliciousAddressBlacklist` | Known malicious address check (always-on) | `enabled` |

### Rule Structure

Each rule has:
- **`action`** —`accept` or `reject`
- **`criteria`** —array of conditions (all must match for the rule to fire)
- **`description`** —human-readable label (optional)
- **`enabled`** —toggle without deleting (optional)

### Full Example

A production policy for a trading bot:

```json
{
  "rules": [
    {
      "description": "Block blacklisted addresses",
      "action": "reject",
      "criteria": [
        {
          "type": "evmAddress",
          "operator": "in",
          "addresses": [
            "0x000000000000000000000000000000000000dEaD"
          ]
        }
      ]
    },
    {
      "description": "Allow Uniswap V3 Router swaps under 1 ETH",
      "action": "accept",
      "criteria": [
        {
          "type": "evmAddress",
          "operator": "in",
          "addresses": ["0xE592427A0AEce92De3Edee1F18E0157C05861564"]
        },
        {
          "type": "ethValue",
          "operator": "<=",
          "value": "1000000000000000000"
        }
      ]
    },
    {
      "description": "Allow ERC-20 transfers under $500",
      "action": "accept",
      "criteria": [
        {
          "type": "evmFunction",
          "selectors": ["0xa9059cbb"]
        },
        {
          "type": "maxPerTxUsd",
          "maxUsd": 500
        }
      ]
    },
    {
      "description": "Rate limit to 20 tx/hour",
      "action": "reject",
      "criteria": [
        { "type": "rateLimit", "maxPerHour": 20 }
      ]
    },
    {
      "description": "Block everything else",
      "action": "reject",
      "criteria": []
    }
  ]
}
```

<Tip>
  The last rule with empty criteria acts as a default deny. If no previous rule matched, this catches everything. Always end your rule set with a catch-all.
</Tip>

## Simple Policies

For simple use cases, Guardian supports individual policies per signer. These are standalone rules — no ordered evaluation, just pass/fail checks on each transaction.

| Type | Config | What It Does |
|------|--------|-------------|
| `spending_limit` | `{ maxWei: "..." }` | Max per-transaction value |
| `daily_limit` | `{ maxWei: "..." }` | Rolling 24h spend cap |
| `monthly_limit` | `{ maxWei: "..." }` | Rolling 30-day spend cap |
| `allowed_contracts` | `{ addresses: [...] }` | Allowlist of contract addresses |
| `allowed_functions` | `{ selectors: [...] }` | Allowlist of function selectors |
| `blocked_addresses` | `{ addresses: [...] }` | Blocklist of destination addresses |
| `rate_limit` | `{ maxPerHour: N }` | Max signing requests per hour |
| `time_window` | `{ startHour, endHour }` | UTC hours when signing is allowed |

Legacy policies are evaluated alongside rules engine policies. Both must pass.

## Audit Trail

Every signing request is logged. Approved or denied. The audit log records:

- Which guardrails were evaluated
- Which violations occurred
- Evaluation time in milliseconds
- The decoded transaction (to, value, function, calldata)
- Final status (approved, denied, broadcast, failed)

Nothing is silent. Every decision is recorded.
